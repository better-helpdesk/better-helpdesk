---
title: Sign customers in from another origin
description: Let a widget on another origin know who your signed-in customer is, with a short-lived token your backend signs.
---

On its own origin, the widget's requests carry your session cookie and `identify` sees who is signed in. On another origin, including another subdomain of your domain, the browser sends no cookies with them, and every customer arrives as an anonymous visitor. An identity token closes that gap: your backend signs who the customer is, and the widget sends the token along with each request.

This guide assumes the widget already runs on the other origin, as in [Add the widget](/docs/guides/widget#on-another-origin).

## Create the secret

The helpdesk and the backend that signs tokens share one secret. Every signed-in customer holds a token signed with it, so it must resist offline guessing, and `buildHelpdesk` refuses one shorter than 32 bytes. Generate one:

```sh
openssl rand -base64 32
```

Store it as `HELPDESK_IDENTITY_SECRET` in both places, and hand it to the helpdesk as [`identityTokenSecret`](/docs/reference/configuration#routing-and-identity):

```ts title="lib/helpdesk.ts"
export const helpdesk = buildHelpdesk({
  // ...
  identityTokenSecret: process.env.HELPDESK_IDENTITY_SECRET,
});
```

## Sign a token for the customer

Wherever your backend renders the page that carries the widget, sign a token for the signed-in user:

```ts title="lib/identity-token.ts"
import { signIdentityToken } from 'better-helpdesk';

export function identityTokenFor(user: {
  id: string;
  email: string;
  emailVerified: boolean;
  name: string;
}) {
  return signIdentityToken(
    {
      sub: user.id,
      email: user.email,
      email_verified: user.emailVerified,
      name: user.name,
    },
    process.env.HELPDESK_IDENTITY_SECRET!,
    { expiresInSeconds: 3600 }
  );
}
```

`sub` is the user's id in your app, the same id `identify` returns as `user.id`, so the customer keeps one contact whether they write in from your app or from the other origin. Set `email_verified` only when your app has proven the address. Add `orgs`, as `[{ id, name }]`, to let the customer pick their organization and share conversations with it; like `orgs` from `identify`, it must list only organizations the user is an active member of. `locale` is also accepted. Without `expiresInSeconds`, a token lasts an hour. [`signIdentityToken`](/docs/reference/exports#signidentitytoken) lists every claim and its limits.

### Without the package

A backend that does not have `better-helpdesk` installed can sign the same token with any JWT library. The token is HS256, and `sub` and `exp` are required. With `jose`:

```ts
import { SignJWT } from 'jose';

const token = await new SignJWT({
  email: user.email,
  email_verified: user.emailVerified,
  name: user.name,
})
  .setProtectedHeader({ alg: 'HS256' })
  .setSubject(user.id)
  .setExpirationTime('1h')
  .sign(new TextEncoder().encode(process.env.HELPDESK_IDENTITY_SECRET!));
```

## Hand the token to the widget

In React, pass it as `identityToken`. A server component can sign it while it renders:

```tsx title="app/layout.tsx"
import { HelpdeskWidget } from 'better-helpdesk/widget';
import type { ReactNode } from 'react';

import { identityTokenFor } from '@/lib/identity-token';

export default async function RootLayout({ children }: { children: ReactNode }) {
  const user = await getCurrentUser(); // however your app does it
  return (
    <html lang="en">
      <body>
        {children}
        <HelpdeskWidget
          api="https://app.example.com/api/helpdesk"
          inbox="support"
          identityToken={user ? identityTokenFor(user) : undefined}
        />
      </body>
    </html>
  );
}
```

With the script tag, add `data-identity-token="…"`. On the element itself, the attribute is `identity-token`.

## Refresh it before it expires

The helpdesk refuses an expired or forged token with 401, and every request the widget makes with it fails. The widget reads the token afresh for each request, so replacing it is enough: render `HelpdeskWidget` with a new `identityToken`, or set the attribute on the element:

```ts
document.querySelector('helpdesk-widget')?.setAttribute('identity-token', freshToken);
```

## What the token does not do

The helpdesk looks at the token only when `identify` returns `null`, so on your own origin the session still decides. A token never grants the agent UI, whatever it contains: agents sign in through `identify` alone. [Identity and trust](/docs/concepts/identity) explains how customers, visitors and agents are told apart.
