---
title: Run jobs and retention
description: Call runJobs on a schedule so emails go out, reminders fire, snoozes wake and old conversations are deleted.
---

Better Helpdesk runs no background process. Work that should not hold up a request is queued in the `helpdesk.job` table, and nothing happens to it until your app calls `helpdesk.runJobs()`. Every email goes through that queue, so does AI triage, and the same call wakes snoozed conversations, queues reminders and applies retention. Run it every minute or every few minutes. [How it works](/docs/concepts/how-it-works#what-runs-where) explains why this work waits for your scheduler.

## Pick a scheduler

<Tabs items={['Long-running server', 'Vercel cron', 'Any other scheduler']}>
<Tab value="Long-running server">

When `next start` runs as a server that stays up, start a timer from Next.js's `instrumentation.ts`:

```ts title="instrumentation.ts"
export async function register() {
  if (process.env.NEXT_RUNTIME !== 'nodejs') return;
  const { helpdesk } = await import('./lib/helpdesk');
  setInterval(() => {
    helpdesk.runJobs({ budgetMs: 20_000 }).catch(error => {
      console.error('[helpdesk] jobs run failed', error);
    });
  }, 60_000).unref();
}
```

The budget stays under the interval, so runs do not pile up. Several containers can run this at once: jobs and reminders are claimed in the database, so each is done once.

</Tab>
<Tab value="Vercel cron">

A route that Vercel's cron calls, protected by the `CRON_SECRET` Vercel sends as a bearer token:

```ts title="app/api/cron/helpdesk/route.ts"
import { helpdesk } from '@/lib/helpdesk';

export const maxDuration = 30;

export async function GET(request: Request) {
  const expected = `Bearer ${process.env.CRON_SECRET}`;
  if (request.headers.get('authorization') !== expected) {
    return new Response(null, { status: 401 });
  }
  return Response.json(await helpdesk.runJobs({ budgetMs: 20_000 }));
}
```

```json title="vercel.json"
{ "crons": [{ "path": "/api/cron/helpdesk", "schedule": "*/5 * * * *" }] }
```

Keep `maxDuration` above the budget: a run checks the budget before each batch of jobs, so the last batch can finish after it. A schedule of every five minutes needs a Vercel plan that allows it; the Hobby plan runs cron jobs at most once a day.

</Tab>
<Tab value="Any other scheduler">

The handler has a jobs route of its own. Set a secret:

```ts title="lib/helpdesk.ts"
export const helpdesk = buildHelpdesk({
  // ...
  jobsSecret: process.env.HELPDESK_JOBS_SECRET,
});
```

and have your scheduler POST to it:

```sh
curl -X POST \
  -H "Authorization: Bearer $HELPDESK_JOBS_SECRET" \
  https://app.example.com/api/helpdesk/jobs/
```

The route runs with the default budget of 20 seconds, so give the scheduler a timeout above that. Without [`jobsSecret`](/docs/reference/configuration#conversations), the route answers 401.

</Tab>
</Tabs>

## Read what a run did

`runJobs` returns a report, which the HTTP route and the cron route above send back as JSON:

```json
{ "woken": 0, "reminders": 1, "retention": 0, "jobs": 4, "failed": 0, "errors": [] }
```

`errors` names a step that threw (`wake`, `reminders` or `retention`); the error itself is logged, and the run goes on with the next step. [Jobs](/docs/reference/routes#jobs) in the routes reference describes every field.

## Delete resolved conversations after a while

Without [`retentionDays`](/docs/reference/configuration#conversations), conversations are kept for good. With it, each run deletes resolved conversations that many days after they were resolved:

```ts title="lib/helpdesk.ts"
export const helpdesk = buildHelpdesk({
  // ...
  retentionDays: 365,
});
```

Their messages and attachments go with them. Files are deleted from your storage first, so a storage failure leaves the rows in place for the next run to try again. A conversation a customer reopens is no longer resolved, and its clock starts again when it is resolved next.

To delete one person's or one organization's data on request, use `deleteContact` and `deleteCompany`, as in [Call the helpdesk from your own code](/docs/guides/own-code#delete-a-customers-data).

## Find jobs that failed

A job whose handler throws is tried again after 2, 4, 8 and 16 minutes. After the fifth failed attempt it is parked: it stays in the table with its last error and is never claimed again. To see the parked ones:

```sql
SELECT kind, payload, attempts, last_error, created_at
FROM helpdesk.job
WHERE run_at = 'infinity'
ORDER BY created_at DESC;
```

Once the cause is fixed, a parked job can be put back in the queue:

```sql
UPDATE helpdesk.job SET run_at = now(), attempts = 0 WHERE run_at = 'infinity';
```

The `helpdesk.job` table and its columns are described in [Database](/docs/reference/database).
